# 要件定義書：問い合わせ管理システム（MVP）

**文書バージョン：** 1.0
**作成日：** 2026-05-10
**ステータス：** 確定

---

## 1. システム概要

### 1.1 背景・目的

現状、運用・保守中のシステムへの問い合わせはSlackで受け付けているが、Excelによる管理が形骸化しており、対応漏れや状況の不可視化が課題となっている。

本システムは、問い合わせの**受付から完了までのライフサイクルを一元管理**し、対応漏れの防止・対応状況の可視化・分析を実現することを目的とする。

### 1.2 将来計画

本MVPは問い合わせ管理に特化するが、将来的には**障害管理機能と統合**し、運用・保守業務を包括的に支援するプラットフォームへ拡張する。

### 1.3 MVPのスコープ

| 対象 | 内容 |
|------|------|
| **IN（MVP対象）** | 問い合わせ管理、担当者アサイン、ステータス管理、ダッシュボード、マスタ管理 |
| **OUT（将来対応）** | 障害管理、Slack Bot自動連携、顧客（エンドユーザー）向けポータル、SLAアラート、通知機能（メール・Slack） |

---

## 2. 用語定義

| 用語 | 定義 |
|------|------|
| 問い合わせ | 顧客企業から受け付けた質問・依頼・バグ報告などの1件 |
| チケット | 問い合わせをシステム上で管理する単位 |
| 担当者 | チケットに対応するサポートチームのメンバー |
| システム | 運用・保守対象のシステム（5〜6本）。顧客企業に紐づく |
| 顧客企業 | 問い合わせを行う顧客の企業単位。1社が複数システムを持つ |

---

## 3. 対象ユーザー

| ユーザー種別 | 説明 | MVP対象 |
|-------------|------|---------|
| 担当者 | 問い合わせを受け付け・対応するチームメンバー | ✅ |
| 管理者 | ユーザー・マスタ管理、全チケット閲覧・操作が可能 | ✅ |
| 顧客（エンドユーザー） | 問い合わせを起票する側 | ❌（将来対応） |

---

## 4. 業務フロー

```
Slackで問い合わせ受信
    ↓
担当者がアプリにチケット手動登録
（顧客企業を選択 → システムを選択 → 種別・優先度等を設定）
    ↓
管理者 or 担当者が担当者をアサイン（対象システムの担当者プールから選択）
    ↓
対応開始（ステータス：対応中）
    ↓
顧客への回答・確認（ステータス：確認待ち）
    ↓
解決確認・クローズ（ステータス：完了）
```

## 5. 機能要件

### 5.1 チケット管理

#### 5.1.1 チケット登録

| 項目 | 内容 |
|------|------|
| 顧客企業 | マスタから選択（必須）。選択後、システム候補を絞り込む |
| システム | 選択した顧客企業に紐づくシステムから選択（必須） |
| 種別 | 操作方法の質問 / バグ報告 / 設定変更依頼 / データ修正依頼（必須） |
| 優先度 | 高 / 中 / 低（種別に応じてデフォルト値を自動設定、手動変更可） |
| タイトル | 問い合わせの概要（必須） |
| 詳細内容 | 問い合わせの詳細（任意） |
| 担当者 | 対象システムの担当者プールから選択（任意、後からでも設定可） |
| 添付ファイル | スクリーンショット等（任意） |
| 受付日時 | 登録時に自動セット（手動変更可） |

**優先度のデフォルト値：**

| 種別 | デフォルト優先度 |
|------|----------------|
| バグ報告 | 高 |
| 操作方法の質問 | 中 |
| 設定変更依頼 | 中 |
| データ修正依頼 | 中 |

#### 5.1.2 ステータス管理

```
新規受付 → 対応中 → 確認待ち → 完了
```

| ステータス | 説明 |
|-----------|------|
| 新規受付 | チケット登録直後の初期状態 |
| 対応中 | 担当者が対応を開始した状態 |
| 確認待ち | 顧客への回答後、確認を待っている状態 |
| 完了 | 問い合わせが解決しクローズされた状態 |

- ステータス変更時は変更日時・変更者を記録する
- 完了後の再オープン（完了 → 対応中）を可能とする

#### 5.1.3 チケット一覧・検索

以下の条件で絞り込み・検索が可能であること。

- ステータス
- 優先度
- 種別
- 顧客企業
- システム（顧客企業選択に連動して絞り込み）
- 担当者
- 受付日時（期間指定）
- キーワード（タイトル・詳細内容）

#### 5.1.4 チケット詳細・更新

- 全項目の閲覧・更新が可能
- 対応履歴（コメント）を時系列で追記できる
- 変更履歴（誰がいつ何を変更したか）を記録・閲覧できる

---

### 5.2 担当者・チーム管理

- 各システムに担当者プールを設定できる（1人が複数システムに所属可能）
- チケットの担当者は対象システムの担当者プールから選択する
- 担当者変更時は変更履歴を記録する

---

### 5.3 マスタ管理

**エンティティ関係：**
```
顧客企業（1） ──< システム（多） ──< 問い合わせ（多）
                        |
                   担当者プール
```

#### 5.3.1 顧客企業マスタ

| 項目 | 内容 |
|------|------|
| 顧客企業名 | 必須、一意 |
| 備考 | 任意 |
| 有効・無効 | 無効化で選択候補から非表示 |

- 1社が複数システムを持てる
- 顧客企業単位で問い合わせ一覧の絞り込みが可能

#### 5.3.2 システムマスタ

| 項目 | 内容 |
|------|------|
| システム名 | 必須。同一顧客企業内でユニーク |
| 顧客企業 | 紐づく顧客企業（必須）。変更不可（変更時は再作成） |
| 説明 | 任意 |
| 担当者プール | 担当者の紐付け（複数可） |
| 有効・無効 | 無効化で選択候補から非表示 |

#### 5.3.3 ユーザーマスタ（担当者）

| 項目 | 内容 |
|------|------|
| 氏名 | 必須 |
| メールアドレス（ログインID） | 必須、一意 |
| パスワード | 必須（ハッシュ管理） |
| ロール | 管理者 / 担当者 |
| 有効・無効 | 無効化でログイン不可 |

---

### 5.4 ダッシュボード・レポート

#### 5.4.1 リアルタイムダッシュボード

- 未対応（新規受付）件数
- 対応中件数
- 確認待ち件数
- システム別・種別別の内訳

#### 5.4.2 月次レポート

- 月別問い合わせ件数推移（グラフ）
- 顧客企業別件数推移
- システム別件数推移
- 種別別件数推移

#### 5.4.3 分析ビュー

- 顧客企業別 × システム別 の件数集計
- システム別 × 種別 のクロス集計
- 担当者別の対応件数

---

### 5.5 認証・アクセス制御

- ローカル認証（メールアドレス＋パスワード）
- セッション管理（一定時間で自動ログアウト）
- ロールによるアクセス制御

| 機能 | 管理者 | 担当者 |
|------|--------|--------|
| 全チケット閲覧 | ✅ | ✅ |
| チケット登録・更新 | ✅ | ✅ |
| マスタ管理 | ✅ | ❌ |
| ユーザー管理 | ✅ | ❌ |
| レポート閲覧 | ✅ | ✅ |

---

## 6. 非機能要件

### 6.1 パフォーマンス

- チケット一覧の表示：3秒以内
- 検索結果の返却：3秒以内
- 同時接続ユーザー数：〜20名程度（MVP想定）

### 6.2 セキュリティ

- パスワードはbcrypt等でハッシュ化して保存
- HTTPS通信必須
- SQLインジェクション・XSS対策を実装
- 操作ログ（ログイン・ログアウト・主要操作）を記録

### 6.3 可用性

- 目標稼働率：99%以上（業務時間帯）
- バックアップ：日次でDBバックアップを取得

## 7. インフラ・技術要件

### 7.1 技術スタック

| レイヤー | 技術 |
|---------|------|
| フロントエンド | Next.js |
| バックエンド | Go |
| データベース | PostgreSQL（RDS） |

### 7.2 インフラ構成（AWS）

| コンポーネント | サービス（案） |
|--------------|--------------|
| フロントエンド | Vercel or S3 + CloudFront |
| バックエンドAPI | ECS（Fargate）or EC2 |
| データベース | RDS（PostgreSQL） |
| 認証セッション管理 | バックエンドで管理（JWT or Cookie） |

### 7.3 API方針

- フロントエンド（Next.js）とバックエンド（Go）はREST APIで連携
- バックエンドはJSON APIを提供する
